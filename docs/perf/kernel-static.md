# Static kernel comparison (#1148, phase 1)

Our kir kernels compared as compiled artefacts against FlashInfer 0.7.3, Triton 3.8.0 and the vLLM 0.34 prebuilt kernels, for three targets, with no GPU: nothing is launched and no CUDA context is created. The question is where the kir output is structurally behind, and what compiler passes would close it. Timed runs are phase 2.

- Date 2026-11-23, commit 060c775 (branch `issue-1148-kernel-level-side-by-side-our-kir-kernel`).
- Generated tables: [kernel-static-tables.md](kernel-static-tables.md). This file is the reading of them.
- Command (about 8 minutes, CPU only, deterministic: two runs give the same tables byte for byte):

```bash
CARGO_TARGET_DIR=/mnt/data/cargo-target/inference-bench-1148 crates/specrt/scripts/kernel_static.sh /tmp/kernel-static docs/perf/kernel-static-tables.md
```

## How it works

| Step | File | What it does |
| --- | --- | --- |
| Our kernels | `crates/specrt/tests/kernel_static.rs` | For each target, builds the real modules (`Module::generate_kv`, kv_planes 1, max_ctx 32768) for 27B NVFP4 (f16 and fp8 KV), Qwen3.5-4B bf16, 122B NVFP4 (256 and 128 experts), gpt-oss-20b, GLM-4.5-Air, and 27B layouts with head_dim 128 at GQA 8:1 and 4:1, plus `add_rmsnorm` at hidden 2560 and 5120. Compiles each one to a cubin with NVRTC the way `Jit` does (`specrt::jit::cubin_for`, `sm_XXXa` when the module needs arch features) and writes a manifest with the launch geometry the runtime uses for each row (grid, block, dynamic smem, shape). The non-ignored test checks every row names a kernel its module builds and that every family has rows on sm_12x. |
| FlashInfer | `scripts/kernel_static_theirs.py` | Generates FlashInfer's own JIT sources (`gen_batch_decode_module`, `gen_batch_prefill_module("fa2")`, norm, rope, `silu_and_mul`) with `CUDA_VISIBLE_DEVICES=` and `FLASHINFER_CUDA_ARCH_LIST`, reads its ninja flags and compiles the kernel translation units to cubins with nvcc for each target. Writes into a scratch workspace, never `~/.cache/flashinfer`. |
| Triton | `scripts/kernel_static_triton.py` | The standard reference kernels (rmsnorm, fused add rmsnorm, silu and mul, rotary, softmax top k, grouped matmul at the tutorial tile configs) compiled with `triton.compile(ASTSource(...), target=GPUTarget("cuda", cc, 32))`. No device needed. Pointer args carry `tt.divisibility=16`, the hint Triton's JIT adds at launch for aligned tensors; without it the matmul compiles to 32 bit loads and the comparison is unfair. |
| vLLM | `kernel_static.sh` | `cuobjdump -xelf all` of `_C_stable_libtorch.abi3.so` and `_moe_C_stable_libtorch.abi3.so` (these ship sm_75, sm_80 to sm_90a and sm_120 cubins). |
| Analysis | `scripts/kernel_static.py` | Per kernel: registers, shared memory (static plus the dynamic amount the launcher passes), spill (LOCAL plus STACK), blocks per SM from registers, smem and threads with each target's limits, the largest backward-branch loop in the SASS ("hot loop") with its instruction mix and a cycle estimate, and a roofline row from algorithmic bytes and FLOPs. Picks the competitor instantiation the competitor's own dispatcher would choose for our shape (FlashInfer decode: `vec_size`, `bdx`, `bdy = group`, `bdz`, 2 stages; FlashInfer prefill: `FA2DetermineCtaTileQ` and the `NUM_MMA_KV` smem rule). |

Targets. kir builds a `Target::cuda(cc, sms, smem)` and the emitters only read it, so a target is a row in `gpus()` in `kernel_static.rs`, not a device.

| Name | Machine | SMs | Opt-in smem | DRAM GB/s | Dense tensor peak used | Source |
| --- | --- | --- | --- | --- | --- | --- |
| sm_120 | desktop RTX PRO 6000 Blackwell Max-Q | 188 | 99 KB | 1792 | FP4 1755, bf16 439 TFLOP/s; FP32 110 | nvidia.com Max-Q page (1792 GB/s, 3511 sparse FP4 TOPS), clocks and SMs from nvidia-smi |
| sm_121 | Spark GB10 | 48 | 99 KB | 273 | FP4 500, bf16 125 | DGX Spark spec (273 GB/s, 1 PFLOP sparse FP4) |
| sm_75 | Windows box RTX 2060 | 30 | 64 KB | 336 | none (no bf16 or FP4 tensor cores); FP32 6.5 | TU106 spec |

Tools: NVRTC 13.2 (`/usr/local/cuda`, the one `specrt` loads), nvcc and ptxas 13.2 for FlashInfer, Triton 3.8.0 with its bundled ptxas, `cuobjdump` and `nvdisasm` 13.2.

What the numbers mean and what they do not:
- "Hot loop cycles" is the sum of the stall counts ptxas wrote into the SASS control bits (4 bits per instruction, minimum 1) over the largest loop. It is ptxas's own schedule, not latency: a load that waits on memory shows as one instruction plus a later barrier wait, not as hundreds of cycles. Use it to compare two kernels' loop bodies for the same work, never as time.
- Bytes are algorithmic (each input read once, each output written once), at the dtypes each side really uses. Our elementwise kernels read and write f32 rows, FlashInfer and vLLM read and write bf16. That is a 2x byte difference for the same op, and it is a design choice of the runtime (f32 residual stream), not a kernel defect. It is called out where it matters.
- The roofline columns are the time floor at peak, not a prediction of our time. Phase 2 measures the fraction of it each kernel reaches.

## Across targets

- sm_120 and sm_121 get byte identical source for every spec here. The only target-driven inputs are `sm_count` (GEMM variant and split choice) and `smem_limit`, and with 188 or 48 SMs the same variants are picked for these shapes. So registers, spills and occupancy are the same on the Spark. The Spark's 273 GB/s against 1792 makes every decode kernel 6.6x more memory bound, so the decode attention occupancy gap costs more there, not less.
- sm_75 (the RTX 2060): only gpt-oss-20b and the standalone `add_rmsnorm` build. Every other module fails at plan time: `flash_attention` (the scalar prefill fallback) needs 84 KB of shared memory against the 64 KB the target allows, and the GDN chunk kernels need `Mma16816`. So there is no Turing path for any Qwen3.5 or 27B model: the scalar fallbacks exist but their tile is sized for sm_80 and up. That is a kernel selection gap, not a kernel quality gap.
- Build determinism: the JIT compiles with `--split-compile=8`. With split compile, `flash_mma` from byte identical source got 32, 56 or 112 B of stack depending on which other kernels shared the module (122B with 256 experts: 112 B; with 128 experts: 32 B; one job: 56 B every time). The static dump compiles with one job so its numbers are stable. In the runtime this means a kernel's spill and speed can change when an unrelated kernel is added to the module.

## Ranked structural gaps

Ranked by the time at stake: the roofline floor of the affected rows times how far the structure says we are from it.

1. Decode attention occupancy and spill at head_dim 256 (`batch_decode_attention`, `attention_split` on the 122B). 27B and 4B at 8 seqs by 32k context: 599 us floor per layer call, 64 threads per SM, 208 to 792 B spill. FlashInfer runs 768 to 1152 threads per SM with no spill on the same shapes. This is the largest gap and it is on every hybrid model we serve (16 attention layers of the 27B per step). Pass: register pressure driven re-tiling of the decode block (more warps per KV head with the accumulator split across them, or fewer rows per warp), checked against `Target::max_regs` with spill as a refusal, like the L1 slot fit pass checks smem.
2. NVFP4 prefill GEMM pipeline (`gate_up_f4a_big`, `down_f4a_big`). Compute bound at m=4096 (832 us and 416 us floors on the 27B). Same tensor op as CUTLASS, but CUTLASS feeds it with TMA, a 3 stage mbarrier pipeline and warp specialized producers. Pass: a `Target::has(Tma)` lowering of the GEMM mainloop load (TMA descriptor plus mbarrier stages) behind the existing `Heavy` mainloop, and stage count from smem budget instead of a constant.
3. `moe_route_logits` static shared memory over 48 KB (hidden 3072 and up). A build failure for GLM-4.5-Air and for any bf16 MoE at hidden 4096, and a latent one for the 122B on any target without the `a` features. Fix: dynamic shared memory with the opt-in attribute, or `MOE_LOGIT_TOKENS` from the smem budget. Pass: a static smem check in the kir budget (`Heavy::budget` already does this for GEMMs; route kernels are not lifted).
4. Elementwise and norm kernels use 32 bit loads (`rmsnorm`, `add_rmsnorm`, `swiglu`, `norm_add`, `qk_norm_rope`). Memory bound at small sizes (27B rmsnorm at 4096 rows: 168 MB, 94 us floor in f32). Every competitor uses 128 bit loads. Pass: vectorise the `Compose` and `RowReduce` loops when width and alignment allow (width divisible by 4 and 16 byte aligned rows are known at kir build time), emitting `float4` loads and stores. Second step, independent: keep the row in shared memory between the two passes of `add_rmsnorm` and `norm_add` (FlashInfer's structure) so the second pass reads no DRAM.
5. sm_75 has no working plan for any Qwen3.5 or 27B model (scalar `flash_attention` smem 84 KB over 64 KB; `GdnChunk` needs `Mma16816`). Pass: size the fallback tile from `Target::smem_limit` and refuse the chunk path in favour of the recurrent GDN path when `Mma16816` is missing.
6. Split compile changes register allocation. `flash_mma` spill varies 32 to 112 B with unrelated module content. Pass or option: compile kernels that sit at the register limit (255) in their own translation unit, or drop `--split-compile` for them, so their code does not depend on what else is in the module.
7. `qk_norm_rope` computes `cosf(pos * inv_freq)` per element. At 32k positions the argument reaches tens of thousands of radians for the high frequency pairs, so those take the libdevice range reduction slow path (the 32 B of stack). A cos and sin table per position (FlashInfer and vLLM) or an angle split into integer and fractional turns avoids it. Small kernel, small cost, but it runs once per attention layer per step.
8. NVFP4 GEMV weight loads are 32 bit (`down_proj_f4`: 68 LDG.32 per loop). No competitor to compare with; static evidence only.

## What to time in phase 2 (8 kernels)

Each is a row where the static data leaves real doubt about the speed gap or about which way it points.

1. `batch_decode_attention`, 27B (hd256, group 6), 8 seqs, 1k, 8k and 32k context: against FlashInfer `BatchDecodeWithPagedKVCacheKernel` with its plan. Does 64 threads per SM really cost bandwidth, or does the HMMA path win back what the occupancy loses?
2. `batch_decode_attention`, head_dim 128, GQA 8:1 and 4:1: same comparison where we do not spill.
3. `attention_split` on the 122B shape (hd256, group 16): the 480 B spill case.
4. `gate_up_f4a_big` and `down_f4a_big`, 27B shapes, m = 512, 2048, 4096: against FlashInfer `mm_fp4` (CUTLASS, tactic from its autotuner).
5. `gate_up_mma_big` on the 4B and gpt-oss bf16 shapes: against cuBLAS (torch matmul) and Triton, to re-prove the #991 claim at kernel level.
6. `flash_mma`, 27B hd256, 1k, 4k and 16k tokens: against FlashInfer FA2 prefill. Static says matched; confirm.
7. `rmsnorm` and `add_rmsnorm` at hidden 2560 and 5120, 1 and 4096 rows: against FlashInfer and vLLM, reporting achieved GB/s on the bytes each side moves (f32 against bf16), so the vector load gap is separated from the dtype gap.
8. `gate_up_act_f4` and `down_proj_f4` at batch 1: no competitor kernel exists; time against the roofline only.
