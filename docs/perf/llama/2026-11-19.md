## #813: bf16 prefill GEMM limit (Spark, llama-3.2-1b, 1,024 tokens)

Change kept: bf16 big tile 256x128 (4x2 warps) when n >= 8192, `Tuning::mma_tile`. Paired A/B prefill B/A 1.16 to 1.26 across llama, gemma3, granite, smollm3, phi3; decode flat; KL and greedy identical to the base commit.

`gate_up_mma_big` median 2.07 ms (was 3.14 ms). The kernel runs every mma twice (activation hi and lo bf16 planes, needed for the 1e-3 logits gate), so the tensor work is 2 x 2 x 1024 x 16384 x 2048 = 137 GFLOP: 66 TFLOP/s executed. torch cuBLAS bf16 on the same M, N and doubled K (1024 x 16384 x 4096): 1.79 ms, 77 TFLOP/s. Our kernel is at 85% of cuBLAS for the same tensor work, 0 bytes spilled (127 registers). cuBLAS on the single plane shape (1024 x 16384 x 2048): 0.87 ms, 79 TFLOP/s, which is what vLLM runs. The remaining prefill gap to vLLM and llama.cpp is the split, not the main loop.

Tried, paired A/B, not kept: 3 and 4 stage pipeline, bk 64, 128x256 and 256x256 tiles, register-accumulating the hi/lo part (direct accumulate, 1.01 to 1.04, within noise), wide bk for unsplit tiles. Unsplit activations (`[runtime] unsplit`) reach about 16,000 tok/s on llama but fail the 1e-3 gate on every linear (docs/spark-matrix.md).
