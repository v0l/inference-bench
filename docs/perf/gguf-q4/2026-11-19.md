## #814 follow-up

`gemv_ggr` is now built from the kir gemm prims (`batch_row_ptrs`, `batch_stage`, `batch_loop_head`, `batch_epilogue`, `batch_reduce`) and calls `gg_dequant8` for the weights, so there is one copy of the Q4_K and Q6_K dequant maths. `cuda/gemm/ggml_batch.rs` passes the codegen prim guard without an allowlist entry.

Single-stream decode (graph GEMV path), nsys: `lm_head_norm` 29% (976 us per call), `gate_up_act` 21% (24 us), `qkv_proj_norm` 16% (18.8 us), `down_proj` 15% (17.6 us). The GEMV launch cap for ggml weights was 2 blocks per SM. Alternating 3 rounds of caps 2, 4, 8, 16 (bench, 128 prompt, 256 new):

Cap 8 is kept (about +6% median over 2). `gemv_ggr` at one token is not used for the graph path: it needs the split activation planes, which the graph GEMV does not produce. The perfpass b1 column (233) is the serve-path step, which already runs `gemv_ggr`; the single-stream graph path stays about 300 against llama.cpp 332, held back by the 976 us `lm_head_norm` (151936x1024 Q6_K, roughly 130 GB/s).
