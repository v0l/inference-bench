## #888 batch-1 serve path

Why the two b1 numbers differed: the serve path runs the decode plan at `tokens = 1` through the batched GEMM chooser, which picked `*_ggr8`, the tensor core batch kernel with 8 token columns (7 of them padding). The single-stream graph path uses the `linear_w` and `linear_norm` GEMV prims. The chooser now returns `GemmPath::Ggv` at one token: `gemv_ggv` (kir `Kind::GgmlGemv`, `cuda/gemm/ggml_gemv.rs`) stages the hi and lo activation planes into shared memory once per block and calls the same `DecGgml::rows` fused Q4_K and Q6_K dot as the graph path. It needs K up to 8192 (the shared memory vector), so a down projection at K=17408 on a larger model keeps `*_ggr8`.

Qwen3-0.6B Q4_K_M, Spark, alternating runs, 128 prompt, 128 new, serve batch 1, tok/s. Round 1 had a loaded card (llama.cpp 45) and is dropped.

Serve b1 goes from 0.64 to 0.83 of llama.cpp (+28%); the graph path is 0.92. The 0.95 target is not reached.

Achieved bandwidth: `lm_head` reads 136 MB in about 1.0 ms, 136 GB/s, half of the 273 GB/s roof. A plain 16-byte read kernel reaches 230 GB/s on this card (`kir::cuda::emit_bandwidth`), so the floor for the head is about 600 us. ncu on `lm_head_norm`: 11% memory throughput, 5.6 active warps per scheduler, 89% of stalls waiting on L1TEX scoreboard. The per-layer linears are 5 to 6 MB reads at 18 to 24 us each, about 130 to 170 GB/s, limited by launch tail and latency more than by bandwidth.

Tried, nothing over 5% in 3 alternating rounds: head grid cap 2 to 64 blocks per SM, GEMV rows per warp 1, 2 and 4, batch split target 2 to 16 blocks per SM.

Q6_K 16-byte loads, checked and dropped: the earlier micro benchmark (563 to 610 us) did not read every byte of each block. A faithful one (`crates/specrt/tools/cuda/bw_q6k_head.cu`: all of qh, ql, scales and d per 224-byte block, 2 rows per warp) gives 999 us for the 16-byte layout against 1006 us for the current 8-byte one, 136 GB/s either way, so the head is not limited by load width and the kernel was not built.
