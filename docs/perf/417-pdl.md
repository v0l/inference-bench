# Programmatic dependent launch (#417)

`[runtime] pdl = true` (default off) launches every kernel through `cuLaunchKernelEx` with the programmatic stream serialization attribute, and prefixes each generated kernel with `griddepcontrol.wait`. A kernel also issues `griddepcontrol.launch_dependents` only when its grid fits in one wave (grid blocks <= SM count), so large GEMMs never let the next kernel steal SMs. With pdl off the generated source is unchanged.

Desktop RTX PRO 6000 (GPU1), bench, prompt 128, 256 new tokens, alternating, 3 rounds, `flock /tmp/gpu27.lock`.

## Decode batch 1

| model | pdl off tok/s | pdl on tok/s | change |
|---|---|---|---|
| Qwen3-0.6B bf16 | 855.1, 854.6, 854.5 | 884.8, 883.9, 885.0 | +3.5% |
| 27B NVFP4, trigger at kernel start (first version) | 58.7, 58.2, 58.1 | 57.0, 56.3, 55.8 | -3.5% |
| 27B NVFP4, trigger only for single wave grids | 58.7, 58.2, 58.1 | 58.8, 58.5 (2 rounds) | +0.5% (noise) |

Trigger at kernel start made the 27B 3.5% slower (the fp4 GEMVs rose from about 40 to 91 us median in nsys: `down_proj_f4`, `lin_in_norm` 72 to 126 us, `gate_up_act_f4` 80 to 101 us, because the next kernel's blocks occupied SMs before the current grid had finished). nsys kernel sum 2074 ms on vs 1272 ms off (64 tokens, includes overlap double counting). The single wave rule removes the loss, and 0.6B keeps +3.5% (it was +4.4% with the unconditional trigger).

## Selective PDL by grid size

The wait attribute is now only attached to launches with at most `8 x SM count` blocks (small kernels: norms, gdn, attention split and reduce); big GEMM grids launch plain. In-kernel `launch_dependents` still fires only for grids of at most one wave.

| variant | Qwen3-0.6B tok/s (off 855) | 27B b1 tok/s (off 58.2-58.9) |
|---|---|---|
| attribute on every launch | 885 | 58.5-58.8 |
| attribute only grid <= SMs | 852 (gain lost) | 59.5 |
| attribute only grid <= 8 x SMs (kept) | 885.8 | 59.6 |

27B b8 with the final code, alternating, serve bench: off 592.8, 592.5, 593.6; on (rounds 2-3) 595.8, 595.7 (+0.5%). Round 1 on was disturbed by another job on GPU1 (405.9) and is excluded. The three b1 rounds in the last alternating run (on 42.4, 51.1, 41.7 vs off 58.2, 42.0, 45.2) were taken while another tenant trained on GPU1 and are not usable.

27B text with pdl on and off (greedy, 96 tokens) is identical (same md5 of the generated text).

## Decision

27B gain is +0.5 to +1%, below the +3% bar; Qwen3-0.6B gains +3.6%. PDL stays opt-in per spec or server config (`[runtime] pdl = true`), default off.

## Spark

phi3-mini and Qwen3-0.6B on the Spark were run (3 rounds, pdl on/off, llama.cpp interleaved), but the GB10 was shared with other tenants: llama.cpp itself ranged from 67 to 173 tok/s on Qwen3-0.6B between rounds and ours from 77 to 171 tok/s. No ratio against llama.cpp can be taken from them, so the 0.87-0.88 figure is unchanged and unverified. A quiet-box rerun is needed (`scripts/perfpass.sh qwen3 --host spark`, then the same with `--pdl` added to the bench).
