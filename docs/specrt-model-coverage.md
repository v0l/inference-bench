Downloads are the hub's last-30-day counts. Nothing here was measured by loading weights: every class comes from the model's `config.json` (and the hub's file list for GGUF repos) run through specrt's own checks, `Spec::from_hf_config_serving`, `Vision::from_hf_config` and `Gguf::spec`, with the family specs embedded in this build.

Source: Hugging Face API: pipeline_tag text-generation (sort downloads, limit 1000; sort trendingScore, limit 200), image-text-to-text (downloads 400, trending 100) and any-to-any (downloads 100); downloads are the hub's last-30-day counts.

Selection: top 100 text groups by summed downloads, the top 20 trending text groups not already in, the top 30 vision groups not already in, and every text model in the local hub cache; a group is every repo whose base_model chain ends at the same root; repos whose names look like test fixtures are skipped. Each group keeps the original lab's repo (`base`) and the most downloaded NVFP4, FP8, AWQ, GPTQ and GGUF copy (`nvfp4`, `fp8`, `awq`, `gptq`, `gguf`), plus any copy already in the local hub cache (`disk`).

## Classes

- LOADS: the serving check passes and every input tower the config declares is read.
- LOADS-TEXT-ONLY: the text model passes; a vision or audio tower in the config is refused or not read, so only text input works.
- TOO-BIG: the architecture passes but the weights are more than 90% of one 96 GB card; the why column says how many cards.
- UNKNOWN-QUANT: the architecture passes without the quantisation, the quantisation format is refused.
- REFUSED: the architecture itself is refused; the why column is the exact refusal text.
- UNCHECKED: nothing specrt could check was found: gated with no open mirror, or a GGUF repo whose hub metadata names only the vision projector.
